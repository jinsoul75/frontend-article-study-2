# React Native New Architecture

22년도 3월에 (v0.68)React Native New Architecture를 옵트인으로 써볼 수 있게 되었고 24년도 10월(v0.76) New Architecture가 신규 프로젝트의 기본값으로 전환되었습니다.

React Native New Architecture 대해 좀 더 깊게 알아보기 위해 정리하게 되었습니다.

> **요약**: React Native의 New Architecture는 기존 **_Bridge_** 기반 구조의 근본적인 성능·타입 안정성 문제를 해결하기 위해 나왔습니다. 핵심 변화는 ① 비동기 JSON 브릿지를 없앤 **JSI**, ② 네이티브 모듈을 지연 로딩하는 **TurboModules**, ③ 동기적 렌더링이 가능한 새 렌더러 **Fabric**, ④ 타입 정의로 네이티브 바인딩 코드를 자동 생성하는 **Codegen**입니다. React Native 0.76부터 New Architecture가 신규 프로젝트의 기본값이 됐습니다.

# 1. Old Architecture

React Native는 원래 **JS 스레드와 네이티브(UI) 스레드가 서로 직접 통신하지 못하고, "브릿지(Bridge)"라는 중간 계층을 거쳐서만 대화**하는 구조로 설계됐습니다.

![](https://velog.velcdn.com/images/hyeseon405/post/bfc4411d-e560-49ad-aa66-316c9bf233d3/image.png)

이 구조에는 역할이 다른 스레드 세 개가 관여합니다.

| 스레드            | 하는 일                                            | 나눠진 이유                                                                  |
| ----------------- | -------------------------------------------------- | ---------------------------------------------------------------------------- |
| **JS 스레드**     | React 컴포넌트 로직, 상태 관리, 이벤트 핸들러 실행 | 비즈니스 로직이 무거워도 화면 렌더링 자체는 안 막히게                        |
| **Shadow 스레드** | Yoga로 레이아웃(위치/크기) 계산                    | 레이아웃 계산(특히 복잡한 트리)이 느려도 화면 그리기나 터치 반응은 안 막히게 |
| **Native 스레드** | 실제 뷰 생성/그리기, 터치 감지, 애니메이션         | 사용자가 직접 체감하는 부분이라 최대한 끊김 없이 반응해야 함                 |

- **Native(UI) 스레드**: 플랫폼의 진짜 UI 스레드(iOS Main Thread / Android Main Thread)다. 실제 네이티브 뷰(`UIView`, `View`)를 생성·수정·그리고, 터치·제스처를 감지하며, `UIManager`가 계산된 업데이트 명령을 여기서 실제 뷰에 적용한다. 사용자가 직접 보고 만지는 화면 자체를 담당하므로, 이 스레드가 막히면 화면이 멈추거나 끊겨 보인다.
- **Shadow 스레드**: 레이아웃 계산만 전담하는 백그라운드 스레드다. Facebook이 만든 Flexbox 구현체인 **Yoga 엔진**이 여기서 돌아간다. JS 쪽 컴포넌트 트리를 반영한 가벼운 "Shadow Tree"(실제 뷰가 아니라 `flex`, `width`, `margin` 같은 레이아웃 속성만 가진 트리)를 유지하고, 각 요소의 실제 위치(x, y)·크기(width, height)를 계산해 그 결과를 Native 스레드로 넘긴다.
- JS에서 네이티브 기능(카메라, 위치정보 등)을 호출하거나, 네이티브에서 JS로 이벤트(터치, 레이아웃 변경 등)를 전달할 때마다 **데이터를 JSON으로 직렬화 → 브릿지로 전송 → 반대편에서 역직렬화**하는 과정을 거친다.
- 이 통신은 **항상 비동기(async)**다. JS와 네이티브가 동기적으로 값을 주고받을 방법이 없다.
- 앱 시작 시점에 등록된 **모든 네이티브 모듈을 미리(eager) 로딩**한다 — 실제로 그 화면에서 안 쓰는 모듈까지도

## 1.1 예시: 버튼을 누르면 내부에서 무슨 일이 일어나나

"단순히 버튼 하나 누르는 것"이 Old Architecture에서는 **브릿지를 최소 2번 건너는** 작업입니다. 단계별로 따라가 보면 이렇습니다.

![](https://velog.velcdn.com/images/hyeseon405/post/04cb48a1-0266-46a2-b308-5fdbb717fa9a/image.png)

1. **터치 감지**: iOS/Android의 네이티브 UI 시스템이 터치를 감지하고, 좌표를 기준으로 어떤 뷰(버튼)가 눌렸는지 hit-test로 찾는다.
2. **이벤트를 JS로 전달 (교차 1)**: 네이티브는 이 터치 정보를 직접 처리하지 않고, JSON으로 직렬화해 브릿지를 통해 JS 스레드로 넘긴다. React의 합성 이벤트 시스템이 이를 받아 해당 컴포넌트의 `onPress`를 호출한다.
3. **JS 로직 실행**: `onPress` 핸들러 안에서 `setState`로 상태를 바꾸거나, 카메라·진동·API 호출같은 네이티브 기능이 필요하면 또 한 번 브릿지를 건너(교차 2, 3) 네이티브 모듈을 호출하고 결과를 돌려받는다.
4. **리렌더링 계산**: 상태가 바뀌면 React가 가상 트리를 다시 계산해 "실제로 변경된 부분"만 찾아낸다(diff). 이 결과로 "이 뷰의 이 속성을 이 값으로 바꿔라"는 업데이트 명령 집합이 만들어진다.
5. **UI 업데이트를 네이티브로 전달 (교차 4)**: 이 명령들도 JSON으로 직렬화되어 브릿지를 통해 네이티브 측 `UIManager`에 전달된다. 레이아웃이 바뀌었다면 Shadow 스레드의 Yoga 엔진이 위치·크기를 다시 계산한다.
6. **화면 갱신**: `UIManager`가 실제 네이티브 뷰(iOS `UIView` / Android `View`)의 속성을 바꾸고, 네이티브가 화면을 다시 그려 사용자 눈에 보이는 버튼의 모양이 변한다.

> 버튼 하나 누르는 가장 단순한 상호작용에도 최소 2번(터치 전달 + UI 업데이트 전달), 네이티브 모듈까지 호출하면 최소 4번 브릿지를 건너야 합니다. 리스트를 빠르게 스크롤할 때처럼 이 과정이 초당 수십·수백 번 반복되면, 각 호출마다의 직렬화/역직렬화 비용이 누적되어 프레임 드랍이 체감될 수 있습니다. 이게 2장의 Old Architecture 한계로 이어집니다.

# 2. Old Architecture의 한계

New Architecture가 나온 이유를 이해하려면, Old Architecture(Bridge)가 실제로 어떤 문제를 일으켰는지 아는 게 먼저입니다.

| 문제                                  | 구체적 영향                                                                                                                                              |
| ------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **직렬화 오버헤드**                   | 모든 JS↔Native 통신이 JSON 문자열로 변환돼야 함. 리스트 렌더링, 이미지 처리처럼 데이터가 크거나 호출이 잦은 경우 병목이 심해짐                           |
| **항상 비동기**                       | 네이티브 값을 동기적으로 즉시 읽어야 하는 상황(예: 레이아웃 측정 직후 바로 다음 계산에 반영)을 처리하기 까다로움 — 프레임 드랍, 깜빡임의 원인            |
| **타입 안정성 없음**                  | 브릿지를 건너는 데이터는 컴파일 타임에 타입이 검증되지 않음. JS에서 잘못된 타입을 넘기면 런타임에야 크래시 발생                                          |
| **전체 모듈 즉시 로딩**               | 앱이 실제로 쓰지도 않는 네이티브 모듈까지 시작 시점에 전부 초기화 → 앱 시작 시간·메모리 사용량 증가                                                      |
| **React의 최신 렌더링 모델과 불일치** | React 18의 Concurrent 기능(`Suspense`, `startTransition` 등)은 렌더링을 중단·재개할 수 있어야 하는데, 비동기 브릿지 구조로는 이걸 제대로 지원하기 어려움 |

<aside>
💡

비유하자면 Old Architecture는 "모든 대화를 편지(비동기·직렬화)로만 주고받아야 하는 두 부서"에 가깝습니다. 옆자리에 있어도 편지를 써서 봉투에 넣고(직렬화) 전달하고, 받으면 다시 뜯어서 읽어야(역직렬화) 합니다 — 급한 질문 하나에도 이 과정을 거쳐야 하니 느릴 수밖에 없습니다.

</aside>

# 3. New Architecture — 핵심 구성 요소 4가지

New Architecture는 브릿지를 걷어내고, 그 문제들을 각각 해결하는 4개의 새 구성 요소로 이뤄져 있습니다.

## 3.1 JSI (JavaScript Interface)

브릿지를 대체하는 핵심 기반. **JS 객체가 C++로 작성된 네이티브 객체(HostObject)를 직접 참조하고 메서드를 호출**할 수 있게 해주는 경량 C++ 레이어입니다.

- JSON 직렬화 없이 **직접, 동기적으로** JS와 네이티브가 통신 가능
- "편지"가 아니라 "같은 방에서 바로 대화하는" 구조로 바뀐 것
- JSI 자체는 특정 JS 엔진에 종속되지 않음 (JSC, Hermes 등 모두와 호환)

## 3.2 Fabric — 새 렌더링 시스템

기존 `UIManager`를 JSI 위에 새로 작성한 렌더러입니다.

- 레이아웃/UI 업데이트를 **동기적으로 처리 가능** → React의 Concurrent 렌더링(Suspense 등)과 제대로 맞물림
- React의 Fiber 재조정(reconciler)과 렌더링 파이프라인을 더 긴밀하게 통합
- iOS/Android 간 뷰 관리 방식을 통일해 플랫폼별 동작 차이를 줄임

### Fabric에서 스레드 구조

Old Architecture에서 보았던 JS·Shadow·Native 세 스레드의 역할 분담 자체는 Fabric에서도 개념적으로 그대로 유지됩니다. 레이아웃 계산은 여전히 별도로 처리되고, 실제 화면 렌더링은 여전히 메인(UI) 스레드가 담당합니다. 하지만 스레드끼리 데이터를 주고받는 방식 자체가 달라집니다.

![](https://velog.velcdn.com/images/hyeseon405/post/f5bef75c-e48a-4b25-bf3b-5bf9f5997515/image.png)

- Shadow Tree가 더 이상 JS 쪽에서만 관리되는 개념이 아니라, **C++로 구현된 공유 가능한 불변(immutable) 데이터 구조**로 바뀐다. JS 스레드와 Native 스레드가 이 트리를 JSI를 통해 **직접 참조**할 수 있어서, 트리를 JSON으로 직렬화해 브릿지로 넘기는 과정 자체가 사라진다.
- Fabric은 렌더링 과정을 **Render(JS) → Commit → Mount(Native)** 세 단계로 나눈다.
  - **Render**: JS 스레드에서 React Fiber가 새로운 Shadow Tree를 계산한다.
  - **Commit**: 계산된 트리를 확정하는 단계로, 업데이트의 우선순위에 따라 **동기적으로도, 비동기적으로도** 처리할 수 있다. 이 부분이 React의 Concurrent 기능, 즉 긴급한 업데이트가 먼저 반영되도록 끼어들 수 있게 하는 지점이다.
  - **Mount**: Native(Main) 스레드가 이전 트리와 새 트리를 비교(diff)한 결과를 실제 네이티브 뷰에 적용한다.
- 레이아웃 계산(Yoga)은 여전히 이루어지지만, 이제는 이 C++ 코어의 일부로 처리된다. 별도의 "Shadow 스레드"를 거쳐 JSON을 주고받는 대신, JSI를 통해 필요한 시점에 직접 계산을 요청하고 결과를 받을 수 있다.

> 정리하면: 스레드가 하는 일 자체는 크게 달라지지 않습니다. 핵심 변화는 스레드 사이의 통신이 "메시지 큐 + 직렬화" 방식에서 "같은 C++ 객체를 여러 스레드가 공유 참조하는 방식"으로 바뀌었다는 점입니다. 이 덕분에 1.1의 버튼 클릭 예시에서 여러 번 거쳐야 했던 브릿지 교차가, Fabric에서는 대부분 사라집니다.

## 3.3 TurboModules — 새 네이티브 모듈 시스템

기존 `NativeModules`를 대체합니다.

- 네이티브 모듈을 **앱 시작 시점에 전부 로딩하지 않고, 실제로 처음 사용되는 시점에 지연 로딩(lazy load)** → 시작 시간·메모리 사용량 감소
- JSI를 통해 직접 호출되므로 동기 호출도 가능

## 3.4 Codegen — 타입 안정성 확보

TypeScript/Flow로 작성한 네이티브 모듈·컴포넌트의 인터페이스 명세를 정적 분석해서, **iOS(Objective-C++)/Android(Java・Kotlin) 쪽 바인딩 코드를 빌드 타임에 자동 생성**합니다.

- JS에서 잘못된 타입으로 네이티브를 호출하는 실수를 **런타임 크래시가 아니라 빌드 타임 에러**로 잡아냄
- 개발자가 매번 수동으로 브릿지 바인딩 코드를 작성할 필요가 없어짐 (보일러플레이트 감소)

# 4. Old vs New 비교

| 항목                  | Old Architecture                      | New Architecture                          |
| --------------------- | ------------------------------------- | ----------------------------------------- |
| JS ↔ Native 통신      | Bridge, JSON 직렬화, 항상 비동기      | JSI, C++ 직접 참조, 동기/비동기 모두 가능 |
| 네이티브 모듈         | NativeModules, 시작 시 전부 즉시 로딩 | TurboModules, 사용 시점에 지연 로딩       |
| 렌더링                | UIManager (브릿지 경유)               | Fabric (JSI 기반, 동기 렌더링 가능)       |
| 타입 안정성           | 런타임에만 확인 가능                  | Codegen으로 빌드 타임 타입 검증           |
| React Concurrent 기능 | 제대로 지원 안 됨                     | Suspense 등 정상 지원                     |
| 앱 시작 성능          | 모든 모듈 즉시 초기화로 느림          | 지연 로딩으로 개선                        |

# 5. 왜 New Architecture가 나왔나

New Architecture 도입을 이끈 동기를 정리하면 다음과 같습니다.

- **성능**: JSON 직렬화 병목을 없애고, 필요한 곳에서는 동기 호출을 가능하게 해 UI 반응성과 프레임 드랍 문제를 개선
- **React와의 정합성**: React 18 이후의 Concurrent Rendering(Suspense, transitions)을 제대로 활용하려면 렌더링이 동기적·중단 가능해야 하는데, 기존 브릿지 구조로는 불가능했음
- **시작 성능**: 모든 네이티브 모듈을 미리 로딩하는 대신 필요한 시점에만 로딩(TurboModules)해 앱 초기 구동 시간·메모리 사용량을 줄임
- **안정성**: Codegen을 통한 빌드 타임 타입 체크로, 브릿지 통신에서 발생하던 런타임 타입 불일치 크래시를 줄임
- **플랫폼 확장성**: JSI 기반 구조는 iOS/Android뿐 아니라 다른 out-of-tree 플랫폼(React Native Windows, macOS 등)과의 통합에도 더 유리한 기반이 됨

# 6. 현재 상태 (참고)

- React Native 0.76부터 New Architecture가 **신규 프로젝트의 기본값**으로 바뀌었습니다.
- 서드파티 라이브러리는 TurboModules/Fabric과 호환되도록 마이그레이션이 필요하며, 과도기에는 Old Architecture와의 상호운용을 돕는 **Interop Layer**가 제공됩니다.
